## Goal

- Every Mac holds its own revocable server credential, including a Mac talking to a server on itself; no unauthenticated mode remains (P1-15, P1-16).
- A lost or sold Mac can be cut off from another Mac or from the server host without rotating every other Mac.
- Audio stops accumulating forever: both audio streams auto-delete after a configurable cap (default 90 days), text and metadata are kept forever, and the user can see usage and purge audio on demand (P1-17).
- Cancelled/failed takes stay in history **by design**, are labeled as cancelled/failed everywhere a user can see or play them, and their audio is deletable per record (P1-18 as decided).
- The dev server stops publishing itself to the LAN by default, and plain HTTP outside loopback/Tailscale is warned about loudly instead of silently blessed (06 F5).

## Decisions applied

From `DECISIONS.md` (these override `REPORT.md` recommendations where they differ):

- **Auth: per-device token.** Each Mac gets its own revocable credential; same-Mac unauthenticated access is fixed as part of this (`DECISIONS.md:12`). This reverses the report's cheaper "peer check or unconditional shared token" sizing — budget L, with an API version bump.
- **Retention: cap audio.** Text kept forever; audio auto-deletes after a cap with a usage/purge screen (`DECISIONS.md:13`). Starting cap: 90 days for both audio streams (`DECISIONS.md:32`).
- **Cancel/failure: keep in history.** Cancelled/failed audio staying in history is intended product semantics; the report's "cancel deletes audio" fix for P1-18 is **not** implemented. The work is labeling + deletability + subjecting kept audio to the same retention cap (`DECISIONS.md:14`).
- **Remote transport: Tailscale only.** No built-in TLS in this batch or later; warn loudly on plain HTTP outside trusted networks (`DECISIONS.md:19`).
- **Audience: shareable product** (`DECISIONS.md:8`). Enrollment and revocation must be operable from the app, not only by editing server files; file-level recovery is the fallback, not the primary flow.
- Defaults carried in: unauthenticated health is liveness-only, detailed readiness needs a credential (owned by Batch 3; this batch must not regress it — see Risks); failed-with-audio records get "transcribe again" (Batch 1 owns the requeue; this batch only guarantees the audio it needs is labeled and capped, not silently swept before a retry — see slice 4 note); test-microphone takes excluded from shared history is a decided default but is **not** in this batch's task — see Out of scope.

Chosen defaults where the audits left the mechanism open (no owner input needed; change on request):

- **One API bump, 2 → 3, in slice 2.** The client already hard-gates on exact `apiVersion` (`Sources/Inlay/InlayController.swift:151` `isServerReady`, `:293`), so client+server lockstep is already the contract (`docs/client-server-contract.md:5`). All later Batch 5 additions (retention preference, storage routes) are additive inside v3.
- **The existing single token becomes the admin/bootstrap token**, accepted only for device administration and self-enrollment, never again for dictation/history routes once a client has enrolled. Clients holding it auto-enroll on first v3 connection, so upgrading in place needs no manual re-pairing. Legacy self-enrollment can be closed explicitly (slice 2) — that close step plus revocation is the lost-Mac recovery story.
- **History stays shared across enrolled devices.** Per-device credentials give identity and revocation; they do not scope who may read/delete history or edit shared preferences in this batch. That matches today's shared-history product promise and keeps the slice minimal. The one new ownership rule: only the owning device may mutate its own _non-terminal_ generation (append/finish/cancel/delivery), because idempotency and continuation already trust `device.id` (`Server/src/generation-service.ts:431`, `:1003`).
- **Revocation trust:** any enrolled, non-revoked device may list devices and revoke _another_ device (household full-trust model, same trust level as today's shared delete). The admin token may do everything device-admin related. A device revoking itself is "disconnect this Mac".
- **Retention applies by `createdAt`, uses current shared preferences (not the per-record settings snapshot), and only ever removes audio files of terminal records.** `audioRetentionDays: 0` means "keep forever" for users who want the old behavior back explicitly.

Device routes (new, in `Server/src/http-server.ts` next to the preferences routes at `:120`, all bodies via `validateBody`):

- `POST /v1/devices/enroll` — body `EnrollDeviceRequest { device: DeviceIdentity }`. Allowed for admin actor always; allowed for a device actor **only** if `device.id === actor.id` (that's rotation-by-reenroll, see rotate below — otherwise 403). Rejects with `403 enrollment_closed` if `legacyEnrollmentClosed` and the actor is admin-token-based _new_ enrollment for an unknown id… — simplification to keep this implementable: `close-legacy-enrollment` flips one boolean; when closed, admin-actor enrollment of a **new** device id is refused, but admin can still list/revoke, and file-level recovery (below) remains. Response `201 EnrollDeviceResponse { device: DeviceSummary, token: string }` — the only place a plaintext device token ever appears. Re-enrolling an existing non-revoked id rotates its token (old token dies immediately) and returns `200`.
- `GET /v1/devices` — any actor. Response `DeviceList { devices: DeviceSummary[], legacyEnrollmentClosed: boolean }` where `DeviceSummary = { id, name, createdAt, lastSeenAt?, revokedAt? }`. Never hashes.
- `DELETE /v1/devices/{id}` — admin, or a device actor whose id ≠ target… plus self-revoke allowed (disconnect). Sets `revokedAt`, replaces `tokenHash` with the hash of a random throwaway value (so the row can never authenticate again even if `revokedAt` handling regresses), `204`. Unknown id → `404 not_found`, mirroring `getInternal` (`:206`).
- `POST /v1/devices/close-legacy-enrollment` — any actor (admin or enrolled device). Idempotent `200 DeviceList`. This is the "all my Macs are upgraded; the old shared token must stop working as an enrollment key" button.
- `validateBody` schemas for all of the above are added to `Server/api/openapi.yaml` in this slice (see API/data changes); `device.id`/`device.name` reuse the existing `DeviceIdentity` schema (`Server/api/openapi.yaml:587`) and get the same server-side `validLabel` rules as `create` — factor `validLabel` out of `create` (`:417`) into a module-level function used by both, instead of copying it.

Lost-Mac recovery, server-host path (no new code beyond the above):

- Anyone with server filesystem access always has the admin token file (explicit `--token-file` or `<data-dir>/admin-token`); with it they can list/revoke/close-enrollment from any HTTP client, and enroll a replacement Mac. If the admin token itself is lost but the data dir is intact: stop server, replace the token file contents (≥32 chars), restart — device tokens are unaffected because they live in `devices.json`. If `devices.json` is lost/corrupt: delete it, restart, every Mac re-enrolls with the admin token; history is untouched (device identity on old records is a snapshot, `Server/src/generation-service.ts:470`). All three procedures go into `Server/README.md` (remote-access section around `:146`) in slice 6.

## API/data changes + migration

**API-breaking: yes — one bump, API 2 → 3, in slice 2.** Everything else in the batch is additive within v3. Breaking changes (slice 2):

- **No unauthenticated data routes remain.** Requests that worked tokenless against a loopback `Host` header (`Server/src/http-server.ts:73` today) now get `401 unauthorized`. The only unauthenticated surface is health liveness (Batch 3's split; `Server/Dockerfile:54` depends on it).

Migration from the single token (the sequence an existing install experiences):

1. Operator upgrades the server. On boot: admin token = existing token file (or a freshly created `<dataDir>/admin-token` for previously tokenless installs, path printed at startup); `devices.json` starts empty; `legacyEnrollmentClosed = false`.
2. Each Mac upgrades Inlay. First v3 `checkServer` still presents the old shared token from Keychain, receives `403 enrollment_required`, auto-enrolls its stable `deviceID`/`deviceName`, and overwrites its Keychain entry with its own device token. From that moment that Mac no longer holds the admin token. No user action unless enrollment fails.
3. Previously tokenless same-Mac installs (empty token in the client): first connect gets `401`; the user pastes the admin token once in **This Mac** (the caption says where the file is), and step 2 takes over.
4. When every Mac has connected once, the user taps "Stop accepting it" (`close-legacy-enrollment`) or an admin-token holder calls the route. After that, the old shared token can no longer mint new device credentials; it remains the recovery/admin key for list/revoke.
5. Lost Mac, before or after migration: revoke its device row from another Mac (or with the admin token); if it may still hold the pre-migration shared/admin token in Keychain, also rotate the admin token file on the server host (stop server → replace file contents → start) — device tokens are unaffected. This procedure is documented in `Server/README.md` by slice 6.
6. Retention on upgrade: the first `start()` sweep runs with the decode-default 90 days, so audio older than 90 days is deleted on first v3 boot unless the operator pre-sets `audioRetentionDays`… which they cannot do before the v3 client exists. Mitigation chosen: release notes for the batch must say this plainly, and anyone who wants forever-keeping sets the picker to Forever promptly (it only affects the _next_ daily sweep for records not yet past a shorter cap; already-swept audio does not come back). Operators who need a pre-upgrade opt-out can be told to keep a backup — backups of the data dir are already the documented practice (`docs/architecture.md:74`). If the owner finds first-boot sweeping too aggressive, the one-line variant is: on first boot with a _missing_ `audioRetentionDays` in `preferences.json`, use 90 but skip the boot sweep once (daily sweep still applies from day 2, giving one day to set Forever). Implementer's call between these two; the plan's default is the simple one (sweep at boot), stated here so the choice is explicit rather than accidental.
7. Downgrade: a v2 server pointed at a v3 data dir ignores `devices.json` and the extra optional preference (optional-on-the-wire pays off again), but will serve tokenless/shared-token semantics again — i.e. downgrading silently reopens P1-15/P1-16. State in `Server/README.md` that downgrading across this batch reverts the auth model; do not attempt to prevent it in code.

## Risks

- **`devices.json` is now a startup-critical, security-critical file.** Corruption fails the server closed (by design, slice 2) — total dictation outage until an operator deletes/repairs it, and deleting it forces every Mac to re-enroll. Mitigation: atomic 0600 writes via the proven `atomicPrivateWrite` path, a 64-device cap keeping the file small, and the documented delete-and-reenroll recovery. Do not soften it to quarantine-and-serve.
- **Legacy-enrollment window.** Between server upgrade and "close legacy enrollment", anyone holding the old shared token — including an already-lost Mac whose Keychain holds it — can enroll a fresh device. Auto-enrollment shrinks the window (each upgraded Mac drops the shared token immediately), but the _server_ keeps accepting it for enrollment until closed. The UI nags with a visible row until closed (slice 3); the risk is accepted as the price of zero-touch migration, and slice 6's docs tell operators with a lost device to rotate the admin token file instead of waiting.
- **Admin token on disk next to the data dir** (`<dataDir>/admin-token` for auto-created installs) concentrates recovery power where the recordings already live. Anyone who can read the data dir already has the archive, so this adds little exposure — but note backups of the data dir now also back up the admin credential. `Server/README.md` wording in slice 6 must say so.
- **Auto-enrollment races.** Two server processes never share a data dir (lock, `Server/src/data-lock.ts:7`), but one Mac could double-enroll if `checkServer` overlaps (it is guarded by `isCheckingServer`, `InlayController.swift:284`, and single-attempt-per-pass in slice 3). Re-enroll is defined as rotate on the server, so the worst case is a token written to Keychain being superseded by a second enrollment whose response was lost — leaving the Mac with a dead token and a `401` loop until the user pastes the admin token again. Mitigation inside slice 3: persist the returned token to Keychain _before_ any retry, and treat a subsequent `401` (not `403 enrollment_required`) as "paste the admin token" copy, never as a reason to auto-enroll again.
- **First-boot retention sweep deletes old audio on upgrade** (Migration step 6). This is intended per DECISIONS but irreversible; it is the single most surprising behavior in the batch. Release-note wording is part of slice 6's docs work, and the skip-first-boot-sweep variant is documented there as the fallback choice.
- **Sweep vs. transcribe-again/requeue (Batch 1).** If Batch 1's startup requeue runs after this batch's boot sweep and expects sealed audio for an old failed record, the orders conflict. Slice 4's invariants (terminal-only, past-cap-only, inside the same mutation queue `start()` already uses) keep them composable; the implementer must confirm actual ordering against the stacked Batch 1 diff rather than assuming today's `initialize()` (`:272`, mark-failed) flow.
- **Auth hot path cost.** Every chunk POST (`http-server.ts:143`) now hashes the bearer token and scans ≤64 device hashes with timing-safe compares. That is microseconds against a per-chunk fsync (`generation-service.ts:196` queue); no caching is added. If Batch 4 makes chunks dramatically cheaper, re-measure before optimizing — do not add a token→device cache preemptively (revocation must take effect on the next request).
- **Throttle false positives.** The slice 6 throttle keys on source IP; behind a Tailscale/reverse-proxy hop many clients may share one address, so 10 bad attempts could `429` a household briefly. Five-minute self-healing window, success resets, and it only triggers on _failed_ auth — acceptable; note it in `Server/README.md` if the implementer finds proxy deployments documented there.
- **Storage usage under-reports.** `StorageUsage` counts Inlay-generated audio from in-memory `byteCount`s only; Wispr imported artifacts and `metadata.json`/`transcript.txt` bytes are excluded, so "purge all audio" will not free imported media. The UI labels the numbers as recording audio; do not label them "total server storage", or the screen will promise what purge cannot deliver.
- **Stack drift.** `http-server.ts` and `generation-service.ts` are touched by Batches 1, 3, and 4 before this branch; line anchors will be wrong by implementation time and some hooks (`tick`, mutation queue, health) may be reshaped. Re-read the stacked versions of every file named here before writing code; if Batch 4 split the global mutation queue, device-store writes and the retention sweep must join whichever queue owns record persistence, not reintroduce a global one.

Inlay Dev manual steps for the owner:

1. **Dev bind (slice 1).** Start the dev server; in a browser open `http://localhost:8393/v1/health` — reachable (liveness only). Confirm the printed dev URL is a localhost URL, and that a second machine on the LAN cannot reach `http://<this-mac-lan-ip>:8393/v1/health` until the server is restarted with an explicit `--host`.
2. **Unauthenticated rejection (slice 2).** With no token configured in Inlay Dev, connect: the app must show a credential error, never history or preferences. From Terminal: `curl -i http://localhost:8393/v1/generations` shows `401`; `curl -i -H "Authorization: Bearer wrong" http://localhost:8393/v1/generations` shows `401`.
3. **Same-Mac cannot bypass (slice 2).** `curl -i -H "Host: localhost" http://127.0.0.1:8393/v1/generations` without a token still shows `401` (this was the old tokenless hole).
4. **Auto-enrollment (slices 2+3).** Paste the admin token (`.local/dev-server/token`) into **This Mac** and connect. Expected: connection succeeds without further prompts; relaunch Inlay Dev — still connected; in the Connection section the devices list shows this Mac marked "This Mac"; `.local/verify-batch5-data/devices.json` contains one device with a `tokenHash` and no plaintext token anywhere on disk.
5. **Dictation still works end to end.** With models configured, dictate into a separate editable app and confirm insertion; open History and play the take's audio. (This guards the `create` device-binding against false `device_mismatch` rejections.)
6. **Second device + revocation (lost-Mac drill).** Point a second client data dir (or second Mac) at the same server with the admin token; it enrolls as a distinct device and shares history. From the first Mac, revoke the second device in **This Mac**. Expected: the second client immediately loses access on its next request (`401`, shown as a credential error), the first Mac keeps working, and the revoked row shows its revocation date.
7. **Close legacy enrollment.** Tap "Stop accepting it" for the shared token. Then try to connect a third fresh client data dir using only the admin token — enrollment of the new device must be refused, while already-enrolled Macs continue unaffected. (Reset by using a fresh `--data-dir` for any later steps that need fresh enrollment.)
8. **Retention sweep (slice 4).** On a fresh throwaway data dir: dictate one take; in **Server preferences** set "Keep audio" to 7 days and save; stop the dev server; hand-edit that record's `createdAt` in its `metadata.json` to 30 days ago (throwaway archive only); restart the server. Expected: the history row and its text remain; Open audio buttons are gone; the caption explains audio was removed by the retention setting; the WAV files are absent from `generations/<UUID>/` while `metadata.json` and `transcript.txt` remain.
9. **Usage + purge UI (slice 5).** In **Server preferences**, usage rows show plausible totals matching the takes made; "Delete original audio" removes only originals (inference playback still works, usage drops by the original share); "Delete all audio" removes the rest and usage drops to zero, with all transcripts still present in History.
10. **Cancelled/failed labeling (slice 5).** Cancel a take after release (during processing) and, if reproducible in the dev setup, produce a failed take. Expected: History list rows read "Cancelled"/"Failed" in text (not icon-only); the detail pane carries the kept-audio caption; audio plays; "Delete audio" removes the audio while the row remains; whole-record delete still works from the trash button and its dialog mentions backups.
11. **Throttle (slice 6, optional spot check).** Ten rapid `curl -H "Authorization: Bearer wrong"` calls to `/v1/generations` from one address end in `429`; a correct token after the window (or from a different source) still works.
12. **Persistence across restart.** Restart the dev server and relaunch Inlay Dev: enrolled device still connects with no paste, revoked device still rejected, retention setting and storage usage unchanged.

What static checks cannot prove, to state plainly in the implementation report if not exercised: a genuine second physical Mac, a real Tailscale hop, Keychain prompts after an ad-hoc rebuild, and the sweep's day-2 daily trigger (only the boot sweep is manually observable without clock manipulation).
