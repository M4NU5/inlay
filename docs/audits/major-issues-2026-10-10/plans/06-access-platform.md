## Goal

- Anyone who cannot sustain a right-side modifier hold can still dictate: tap-to-start/stop latch, a real menu-button dictation trigger usable by Voice Control / Switch Control, left-side modifiers, and one recorded non-typing key. Hold and double-tap keep working exactly as today.
- Input Monitoring becomes a labeled, supported clipboard-only mode instead of dead code (`InlayController.swift:1270` currently has no view caller).
- Escape stops cancelling other apps' work: it cancels only while capturing.
- The window becomes keyboard-operable with visible focus, one flat page scaffold with dividers, single-scroll pages, semantic text sizes, one server-status home, and diagnostics behind a disclosure.
- A crash while "mute while recording" is on no longer leaves the Mac silently muted.

## Decisions applied

- **Trigger: latch + menu** (`DECISIONS.md`: "Tap to start, tap to stop, plus a menu-button trigger. Hold still works."). Implemented as a third `HotkeyActivationMode` so hold stays the default and double-tap is untouched.
- **Layout: flat + dividers** (`DECISIONS.md`: "One shared flat page scaffold across all five pages."). Cards (`InlaySettingsGroup`, grouped `Form`) are replaced, not extended.
- **Escape cancels only while capturing** (`DECISIONS.md` defaults). Processing-phase Escape becomes a no-op for Inlay.
- **Mic test stays separate and clearly labeled** (`DECISIONS.md` defaults). The menu gains a real dictation button; `InlayMicrophoneTestButton` keeps its test semantics and its "Test microphone" title everywhere (fixing the mislabeled menu primary button, `01 F9`).
- **Audience: shareable product** (`DECISIONS.md`). Diagnostics become disclosure content, not product UI; permission copy must make sense to a non-developer.
- **Input Monitoring labeled mode** (task + `03 F8` fix direction + REPORT Q7c recommendation "support it with a labeled row"). Tension to resolve explicitly: `DECISIONS.md` defaults also say "Missing Accessibility blocks at key-press with a permission HUD." Chosen reading, applied in Slice 6: the press-block (Batch 2) applies when the user has _no_ usable grant or expects insertion; a user who granted Input Monitoring only is in the labeled clipboard-only mode and is **not** blocked, because their take is usable (copied). If Batch 2 already shipped a blanket press-block, Slice 6 carves out this exemption. This is the only place this plan narrows a DECISIONS default, and it does so to satisfy the explicit Batch 6 requirement.
- **Mute mechanism kept, risk labeled** (REPORT Q15e recommendation; `DECISIONS.md` is silent). No ducking/pause-media rework in this batch.
- **No behavioral automated tests** (`AGENTS.md:4`). Verification is `swift build` + Inlay Dev computer use only. Batch 8's parity-check allowance is not used here; the new config tokens are guarded by the strict decoder, not by a new check.

## Risks

- **Accidental latched recording (Slice 3).** A stray tap now records until tapped again — the exact risk hold mode was designed against. Mitigations already in-tree: latch is opt-in (hold stays default), HUD expanded state + menu-bar status show capture continuously, 180 s hard cap auto-finishes (`InlayController.swift:1322`), and a rejected start cannot latch (`HotkeyMonitor.swift:494` pattern). Residual risk accepted by DECISIONS ("Tap to start, tap to stop").
- **HotkeyMonitor state-machine regressions (Slices 3, 5).** `HotkeyMonitor` is 650 lines of edge-case handling (Fn fast path, watchdog, tap recovery, `awaitingObservedRelease`). Every mode/key addition must go through the existing `beginHold`/`release`/`reset` funnels — no parallel state. The injected `HotkeyMonitorEnvironment` (`:124`) exists so this _could_ be tested, but `AGENTS.md:4` bans behavioral tests; verification is the manual matrix below. Highest-risk specific: `reset(keepLatch:)` (`:620`) and `clearLatchedTake()` (`:504`) missing the new mode would strand or kill latched takes on tap recovery — both are called out line-by-line in Slice 3.
- **Custom-key precedence bugs (Slice 5).** If `customKeyCode` and `key` both drive `beginHold`, a take can double-start or a modifier tap can stop a function-key latch. The plan's rule is strict precedence (custom non-nil wins, modifier path inert); the implementer must gate the `flagsChanged` branch (`:334`) on `customKeyCode == nil`, not just add the keyDown branch.
- **Config downgrade strictness (Slices 3, 5).** New tokens make `config.json` unreadable to older builds (strict decoder, `InlayConfiguration.swift:36`). Bounded harm (last-good fallback), but a user bisecting builds will see their trigger silently revert. Documented in commits; no schema bump because the decoder's version gate (`:32`) would reject the whole file instead of one key.
- **Microphone drag vs page scroll (Slice 8a).** Removing the inner ScrollView can break the drag overlay's coordinate math mid-scroll. `scrollDisabled`-during-drag is mitigation (1); if SwiftUI gesture composition fights it, the fallback (one documented inner region) still satisfies "kill the 270 pt trap" partially. Flag in-commit which path landed.
- **Form → scaffold control behavior drift (Slice 8b).** Grouped `Form` gives label alignment, focus order, and `.disabled` section semantics for free; hand-rolled rows must reproduce them. Keep every `accessibilityIdentifier` byte-identical (they are the owner's computer-use anchors) and re-check Tab order through This Mac after migration.
- **Menu-trigger destination surprise (Slice 4).** Users may expect insertion and get clipboard when no caret was placed first. This is the existing safe fallback, labeled via help text + copied-state handling (Batch 2 attention state), but it is the slice most likely to generate "dictation didn't insert" confusion. The commit and Verification steps both call it out.
- **Batch ordering drift.** Batches 1–5 edit `InlayController.swift` (health-poll, HUD text, press-block), `MenuHUDViews.swift` (stage text, click behavior), and `InlayTheme.swift` (contrast) before this branch. Expect merge-level line drift and possible semantic overlap at `beginDictation` (`:849`), `canCancelWithEscape` (`:150`), and `InlayMenuView` (`:4`). Re-read those three bodies on the stacked base before Slices 1, 4, and 6; do not apply this plan's diffs blind.
- **Sticky Keys / Secure Input behavior is inferred, not verified** (audit-wide caveat). Slice 5 does not claim to fix Sticky Keys; if the owner's device check (Verification) shows latched modifiers confusing `isDown(in:)`, that becomes a follow-up, not a Slice 5 blocker.
