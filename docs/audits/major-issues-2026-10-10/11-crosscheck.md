## Refuted or overstated claims

1. **04 F2 vs 10 F3 — direct contradiction; each is half the truth.** 04 says `events()` "has no overall deadline; a wedged generation blocks all later deliveries" forever; 10 says the client "gives up after 5 stream-recovery fetches" in "~1–2 minutes". Both cite the same loop (`ServerClient.swift:286`–`:313`). The code does both, in different regimes: every successful non-terminal re-fetch resets `recoveryFailures = 0` (`:304`), so a _reachable server with a wedged generation_ loops forever (04's regime); five consecutive _failed_ re-fetches throw (`:309`), so a _server outage_ is abandoned after roughly 5×(≤12 s request + ≤8 s sleep) (10's regime). Neither report mentions the other regime, and both present their half as the behavior. The merged finding is worse than either alone: reachable-but-stuck wedges delivery indefinitely, while a >~100 s outage silently orphans a result that later completes into history.
2. **07 F5's "multi-GB temp WAV" is unreachable as written.** The 768 kHz × 8 ch × 180 s ≈ 4.4 GB figure is correct arithmetic against the duration-only writer cap (`AudioRecorder.swift:481`), but that session cannot survive to write it: the first original chunk above 192 kHz throws in the upload buffer (`ServerClient.swift:407`–`:410`), which fails the session and cancels/discards the recorder (`InlayController.swift:905`–`:909`, `AudioRecorder.swift:616`–`:619`) within the first flush. What remains true and serious is the 192 kHz × 8 ch case dying at ~43 s against the server byte cap. The temp-file sub-claim should be struck.
3. **05 F3 history-size inevitability is overstated (P1 → P2).** The mechanism is real (full records at `generation-service.ts:740`–`:742`; hard 16 MiB client rejection at `ServerClient.swift:160`), but crossing 16 MiB on a 50-record page needs an average of ≥328 KiB per record. The settings snapshot is itself capped at 256 KiB (`generation-service.ts:400`–`:405`), the dictionary at 500 entries (`Server/src/domain/dictionary.ts:3`), speech text at 256 KiB (`native-inference.ts:308`), and persisted metadata at 1 MiB (`generation-service.ts:51`, `:1201`). A page only crosses the cap if essentially every recent record carries a near-maximum dictionary _and_ long transcripts — pathological, not the "as the dictionary grows, eventually" certainty the finding states. Real defect, wrong timeline.
4. **02 F1's "content column jumps sideways" mostly does not occur at the default window size.** The window is created at 940×700 (`InlayApp.swift:108`) with the sidebar at min 210 / ideal 230 (`InlayWindowView.swift:65`), leaving ~710 pt of detail width. At that size the 760/780/800 max-widths never bind, and the 700 page differs by ~10 pt. The jump is real only on windows widened past ~1,030 pt. Combined with the (correct) container-style differences this is a legitimate consistency complaint, but grading it P1 — under 01's key, "loses user work or trust / routinely blocks the core loop" — does not hold. P2.
5. **04 F3's P1 quit-hang has a narrow precondition the grade ignores.** The blocking wait only exists while a Wispr preparation gate is alive; the gate is created only when an import preview is prepared (`InlayController.swift:389`–`:390`) and is `nil` otherwise, in which case quit is unblocked. "Quit blocks the main thread" as a headline reads as an every-quit defect; it is a quit-during-import-prepare defect. Mechanism confirmed, P1 → P2.
6. **06 F4's user story is broader than its (accurate) evidence.** "Start dictating something sensitive, hit cancel — the recording is still on the server" is false for the common cancel: cancelling while capturing deletes the unsealed `.raw` files (`generation-service.ts:1234`–`:1242`). Kept audio requires cancelling _after_ release/seal (Escape or HUD-click during processing) or a processing failure. The evidence bullet scopes this correctly ("a take cancelled after sealing"); the experience paragraph does not.
7. **05 F4's P1 rests on a client that cannot exist today.** The server-only rules are real, but the shipped client cannot trip them: it sends only statuses from `DictationDeliveryStatus` (`AppState.swift:10`–`:12`), all of which are in the server's list (`generation-service.ts:821`–`:830`), and version skew — the audit's stated trigger — is already hard-blocked by the exact `apiVersion` gate (`InlayController.swift:151`) before any of these rules are reached. This is contract hygiene for future clients, P2.
8. **04 F5 (P2) — the one flatly refuted mechanism.** `ConfigurationWatcher.deinit` does iterate `sources` off-queue (`ConfigurationStore.swift:183`), but every mutation of `sources` happens inside `queue.async { [self] in … }` blocks (`:187`, `:201`) that retain the watcher until they run, so `deinit` cannot execute concurrently with one. The claimed Array-storage race is not reachable as written. (Left as a cleanliness nit at most.)

## Major blind spots no reviewer covered

1. **Text-pipeline correctness was routed but never audited.** The inventory routes "Text pipeline quality" to `Server/src/domain/*` (`00-inventory.md:153`), yet across 01–10 those files are cited only for size (08) and one worker-timeout line (07). Nobody read `lists.ts` (897 lines), `correction.ts` (678), or `dictionary.ts` looking for transcript-mangling defects — wrong list renumbering, correction-guard false accepts (number/negation flips the guards exist to prevent), dictionary over-application. For a product whose output is inserted into other people's documents, silent text corruption is at least as damaging as the (well-covered) total-loss paths, and it is completely unexamined. The TS↔Swift pipeline _parity_ question (08 F1/F9) makes this worse: two unaudited implementations.
2. **Insertion safety got surface treatment only.** `TextInserter.swift` (718 lines), `TextDeliveryTransaction`, `NativePasteCommand`, `ConfirmedInsertionRebases`, and `InsertionPreparation` are cited at their edges (blocked reasons, clipboard counts, one `as!` spot-check) but no file audits the wrong-field/wrong-app/protected-field decision logic end-to-end, the clipboard save/restore race window, or the rebase arithmetic for overlapping pending takes. The one component that can put wrong text into a password field or the wrong app has no dedicated verdict.
3. **Untrusted-input parsing of Wispr data.** The client parses a third-party app's SQLite databases and media blobs (`WisprFlowSourceReader.swift`, 1,149 lines) and the server stages/publishes checksummed artifacts (`imports.ts`, 936 lines). Coverage is limited to coupling/size (08 F7), the quit hang (04 F3), one startup-throw (05 F2), and dictionary residue (06 F10). Malformed/hostile local DB robustness, staging-journal crash consistency, and partial-publish states were never examined.
4. **The Swift reference server's actual behavior.** Every applicable file lists parity as unresolved; no one diffed even a single route or the auth/storage paths beyond one middleware spot-check (06). Until that is done, 08 F1's severity — and whether any confirmed TS-server P1 also exists (or is worse) in the identically-named Swift binary — is unknowable from this audit set. This is the largest _known_ unknown and it is currently carried as a footnote in five files.
5. **Client config/data migration.** `ConfigurationFile`/`ConfigurationStore` versioning and last-good behavior are cited for one silent-error UX point (01 F7) but never audited for forward/backward compatibility of `config.json`/`client.json` across the rename the README documents (`README.md:43`–`:50`) — the exact place an upgrade silently resets device identity.
