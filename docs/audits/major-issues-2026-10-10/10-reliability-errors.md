# Reliability, error handling, observability — major-issues audit (2026-10-10)

- Scope: what happens when the server is down, a model is missing, the mic is denied or lost, the insertion target is gone, the disk fills, a long dictation is interrupted, or the app quits mid-recording. Silent failures, unrecoverable states, missing user-facing recovery, and logging gaps.
- Method: every file body cited below was opened and read in this worktree (branch `audit/major-issues`, HEAD `b6d6815`). Line numbers are worktree-relative. No code was executed and no tests were run, per `AGENTS.md:4`; confidence is marked verified-in-code (mechanism read end-to-end) or inferred (mechanism read, magnitude/frequency not observed).
- Headline: no P0 found — the happy path has genuinely careful failure handling (see "Verified strengths"). The major theme is P1 data-loss-on-interruption: at every stage between key-press and insertion, a transient failure discards work that is already durable somewhere, and neither side can explain afterwards what happened because logging is close to zero.

## Findings

### 1. Any mid-take interruption loses the entire dictation, however much was already captured and uploaded

- Severity: P1
- Evidence:
  - Client upload is single-attempt per chunk with no retry: `flush` does one `session.data` and throws (`Sources/Inlay/ServerClient.swift:382`). The upload task's error handler cancels the whole session (`Sources/Inlay/InlayController.swift:905`).
  - A single failed background health poll during capture also kills the take, even if the upload path is healthy (`Sources/Inlay/InlayController.swift:319`), and the poll runs every 5 s (`Sources/Inlay/InlayController.swift:253`).
  - Sleep/lock/power-off and microphone route/device loss take the same path: `restForSystem` fails the session and stops all pending work (`Sources/Inlay/InlayController.swift:1229`); recorder interruption calls `failSession(cancelServer: true)` (`Sources/Inlay/InlayController.swift:822`, origin `Sources/Inlay/System/AudioRecorder.swift:190`).
  - `failSession`/`resetSession` cancel the server generation and cancel the recorder, which discards the local capture file (`Sources/Inlay/InlayController.swift:738`, `Sources/Inlay/InlayController.swift:757`, `Sources/Inlay/System/AudioRecorder.swift:181`, writer discard at `Sources/Inlay/System/AudioRecorder.swift:464`). The server then deletes the partial upload files on cancel (`Server/src/generation-service.ts:798`, cleanup `Server/src/generation-service.ts:1234`), and stranded partial uploads are expired and cleaned by the 2 s tick after 45 s idle / 300 s total (`Server/src/generation-service.ts:296`).
  - This is documented as intended ("There is no offline capture queue or automatic audio-upload retry", `docs/architecture.md:33`), but the building blocks for salvage already exist and are unused: the server accepts idempotent exact chunk replays (`Server/src/generation-service.ts:551`), `finish` is retry-safe and the client does retry it (`Sources/Inlay/ServerClient.swift:236`), and the full take is simultaneously written to a local WAV by `RecordingWriter` (`Sources/Inlay/System/AudioRecorder.swift:377`).
- What the user experiences: a 2:59 dictation (limit is 180 s) destroyed by a Wi-Fi blip, a server restart, AirPods disconnecting, or the lid closing at second 170. Nothing is salvageable from either side; the words must be re-spoken from memory. The bounded upload pipe has the same failure mode by design on slow links: backlog over 512 chunks fails the take rather than pausing capture (`Sources/Inlay/ServerClient.swift:125`).
- Confidence: verified-in-code.
- Suggested fix direction: retry `flush` with backoff using the server's existing idempotent-chunk semantics before failing the session; on capture interruption (route loss, sleep), offer/perform "finish with what was uploaded" — the server can already seal any complete ≥0.25 s interval whose frame counts the client reports; keep the local capture file until the server generation reaches a terminal state so a failed upload can be re-sent as a new generation.
- Effort: M (retry + partial-finish) to L (full local re-upload recovery).
- Owner decision: is "no offline queue, interruption = loss" still the intended product contract now that takes can run 3 minutes and queue serially? See Questions.

### 2. Server shutdown/restart destroys sealed, queued dictations that are already durable on disk

- Severity: P1
- Evidence:
  - `GenerationService.shutdown` cancels **every** non-terminal record, including fully uploaded `queued` and in-flight `transcribing`/`proofreading` generations, before stopping inference (`Server/src/generation-service.ts:315`).
  - On the next start, any record still non-terminal (crash, kill, power loss) is marked `failed` ("Server restarted before this generation completed") and never re-queued (`Server/src/generation-service.ts:272`).
  - The sealed `inference.wav` survives — `cleanPartial` removes only `.raw`/`.partial` files (`Server/src/generation-service.ts:1234`) and the artifact route will still serve the WAV (`Server/src/generation-service.ts:871`) — but no route reprocesses an existing generation: the full route table is `Server/src/http-server.ts:119`–`Server/src/http-server.ts:221`, and processing is only ever enqueued from `finish` (`Server/src/generation-service.ts:703`, `Server/src/generation-service.ts:1014`). A repo-wide search for `reprocess|requeue` in `Server/src` and `Sources/Inlay` finds no such path.
- What the user experiences: dictations queue serially (FIFO, one at a time), so restarting the server — including the documented `./scripts/run-dev.sh restart` upgrade flow, a crash, or a Linux service restart — while takes are queued turns completed recordings into dead history entries. The user can listen to the audio but can never get the transcript without re-speaking it, and nothing in the UI path read here offers "transcribe again".
- Confidence: verified-in-code.
- Suggested fix direction: on startup, re-enqueue generations that were `queued`/`transcribing`/`proofreading` **and** have a sealed `inference.wav` (they are indistinguishable from fresh sealed work); or at minimum add a reprocess action for failed records that retain sealed audio. Keep marking only `receiving` (never sealed) records failed.
- Effort: S–M (re-enqueue on initialize is a small, well-bounded change; the queue and `process` already handle everything downstream).

### 3. Client abandons a pending result after bounded stream recovery, and nothing survives an app relaunch

- Severity: P1
- Evidence:
  - Event-stream recovery gives up after 5 failed record re-fetches (`Sources/Inlay/ServerClient.swift:286`, limit at `Sources/Inlay/ServerClient.swift:309`), with ≤8 s sleeps between attempts (`Sources/Inlay/ServerClient.swift:311`) on a session whose per-request timeout is 12 s (`Sources/Inlay/ServerClient.swift:44`). Total tolerance is on the order of one to two minutes of server unavailability.
  - When it gives up, the pending-dictation task throws, shows "failed", and is removed (`Sources/Inlay/InlayController.swift:1044`). The server keeps processing and completes the generation, but no client state persists the pending generation ID: pending takes live only in memory (`Sources/Inlay/InlayController.swift:172`), and startup recovery consists of deleting orphaned local capture directories (`Sources/Inlay/InlayController.swift:248`, `Sources/Inlay/System/AudioRecorder.swift:35`).
  - By design "Opening history never pastes an old result" (`docs/architecture.md:33`), so even a user who notices must manually find the entry and copy it themselves; nothing surfaces "a dictation finished while you were away and was never delivered".
- What the user experiences: dictate, server restarts or network drops for >~1–2 minutes during queued processing (easy when several takes queue behind 180 s of transcription, or models reload), HUD says the dictation failed — then the finished transcript silently exists in shared history, undelivered and unannounced. The user re-dictates duplicate text or trusts the "failed" message and loses the content. Quitting the app mid-processing lands in the same place (see finding 6).
- Confidence: verified-in-code for the mechanism; the ~1–2 minute bound is inferred from the timeout arithmetic (not measured).
- Suggested fix direction: persist pending generation IDs (client data dir) until delivery is reported; on launch and on reconnect, reconcile them — deliver or explicitly surface completed-but-undelivered results (at minimum a "ready to copy" state, since automatic paste after relaunch would violate the captured-destination safety model). Raise/unbound the recovery budget while the app stays open, since the record fetch is cheap and idempotent.
- Effort: M.

### 4. One corrupt archive file bricks the entire server at startup, with no named culprit and no quarantine

- Severity: P1
- Evidence:
  - Startup loads `preferences.json` and rethrows anything that is not file-not-found (`Server/src/generation-service.ts:216`).
  - Every generation directory's `metadata.json` is parsed and validated during `initialize`; a parse/validation failure rethrows (`Server/src/generation-service.ts:243`), and structurally invalid metadata throws a generic message that does not name the offending generation (`Server/src/generation-service.ts:270`: "A generation has invalid metadata.").
  - The throw propagates through `startServer` (lock released, error rethrown, `Server/src/main.ts:32`) to the entry point, which prints only `error.message` — no file path, no stack — and exits 1 (`Server/src/main.ts:59`).
- What the user experiences: one truncated `metadata.json` (power loss outside the atomic-write window, disk error, manual edit, restore from a partial backup) takes down dictation, history, and preferences for every connected Mac. The only diagnostic is a single console line that may not even say which file is bad; recovery is manual filesystem surgery in the data directory, hunting through UUID folders. There is no skip-and-quarantine, no "start with the readable 99% of the archive".
- Confidence: verified-in-code.
- Suggested fix direction: per-record failure isolation during `initialize`: log the path and reason, rename the bad directory aside (e.g. `<id>.quarantined`), and start with the rest. Do the same "name the file" treatment for `preferences.json`, and print the actionable path at the `main.ts` catch. Consider keeping preferences strict (it is small and singular) but generations must be fault-tolerant.
- Effort: S–M.

### 5. Server runs with logging effectively off; most failures leave no trace anywhere

- Severity: P1
- Evidence:
  - Fastify is constructed with `logger: false` (`Server/src/http-server.ts:60`). The error handler converts every unexpected error to a generic 500 body and discards the error object — no log line, no stack (`Server/src/http-server.ts:97`, fallthrough `Server/src/http-server.ts:111`).
  - The only `console.*` calls in `Server/src` are the four in `Server/src/main.ts:44`–`Server/src/main.ts:60` (help text, listening line, startup-failure message). The generation tick swallows all errors (`Server/src/generation-service.ts:292`), warmup failures are swallowed after being reduced to an in-memory string (`Server/src/generation-service.ts:1249`), and the processing queue swallows its own rejections (`Server/src/generation-service.ts:1025`); `process` persists only `error.message` on the record (`Server/src/generation-service.ts:1129`).
  - Helper diagnostics are deliberately destroyed: child stderr is drained and dropped ("Drain GPU diagnostics without retaining them", `Server/src/inference/helper-process.ts:250`), and the `close` handler ignores the exit code and signal, collapsing every helper death to "Native helper closed its output." (`Server/src/inference/helper-process.ts:256`, `Server/src/inference/helper-process.ts:319`).
  - Client side is barely better: a repo search finds `Logger` only in the audio-capture files (`Sources/Inlay/System/AudioRecorder.swift:141`, `Sources/Inlay/System/AudioRecorder.swift:296`, `Sources/Inlay/System/InputOnlyAudioUnit.swift:216`). Everything else — HTTP failures, delivery failures, controller errors — exists only as a HUD message auto-dismissed after 4 s (`Sources/Inlay/InlayController.swift:1195`) or an `errorMessage` string overwritten by the next event. The one diagnostics surface is explicitly in-memory only ("No persistent log", `Sources/Inlay/System/HotkeyMonitor.swift:207`), capped at 16 entries (`Sources/Inlay/InlayController.swift:1306`).
- What the user experiences: when dictation misbehaves in the field, there is nothing to attach to a bug report. A helper segfaulting on a specific GPU/driver, a recurring 500 on one route, a warmup that fails every morning — all are invisible after the fact, on a product that spans a Swift app, a Bun server, and two native ML processes across two operating systems. The per-generation `metadata.json` provenance (model hashes, timings, rejection reasons) is genuinely good, but it only exists for generations that got far enough to be saved.
- Confidence: verified-in-code.
- Suggested fix direction: structured server logging to stderr (systemd/journal and the dev runner's `.local/server.log` already capture it) covering startup, readiness transitions, helper spawn/exit **with code+signal**, request 5xx with stack, and tick/warmup failures; keep a bounded tail (e.g. last 64 KiB, redacted) of helper stderr per helper and include it in the failure that kills a request. On the client, log controller/ServerClient failures via `Logger` under the existing subsystem and add an "Export diagnostics" action that bundles client log markers, server health, and the failing generation's metadata (never transcript/audio by default).
- Effort: M.

### 6. Quit/crash during a take: cancellation is fire-and-forget, sealed work is abandoned in the UI, and a crash can leave the Mac muted

- Severity: P2 (P1 for users who enable mute-while-recording and crash)
- Evidence:
  - `shutdown()` cancels the active server generation via an unstructured `Task { try? await … }` (`Sources/Inlay/InlayController.swift:790`, cancel at `Sources/Inlay/InlayController.swift:807`), while `applicationShouldTerminate` returns `.terminateNow` unless startup or config writes are pending — in-flight dictation teardown is not waited on (`Sources/Inlay/InlayApp.swift:83`). `stopPendingDictations` likewise fires un-awaited cancels for unsealed takes (`Sources/Inlay/InlayController.swift:1165`). Outcomes are discarded with `try?`, consistent with every other cancel site (`Sources/Inlay/InlayController.swift:709`, `Sources/Inlay/InlayController.swift:762`, `Sources/Inlay/InlayController.swift:1046`).
  - Sealed pending takes are intentionally left to complete on the server (comment `Sources/Inlay/InlayController.swift:802`), but per finding 3 nothing reconciles them on next launch — they complete silently into history.
  - Output-muting state is only an in-memory array (`Sources/Inlay/System/SystemOutputMuter.swift:17`); restore happens on the normal finish/reset paths (`Sources/Inlay/InlayController.swift:747`, `Sources/Inlay/InlayController.swift:944`) and failed un-mutes are retried on the next restore **within the same process** (`Sources/Inlay/System/SystemOutputMuter.swift:33`). The docs concede "A client crash during a take can leave output muted" (`docs/architecture.md:43`), and nothing at launch (`Sources/Inlay/InlayApp.swift:40`, `Sources/Inlay/InlayController.swift:226`) checks for or repairs a mute left by a previous crashed process — the information needed to do so (which elements Inlay muted) is never persisted.
- What the user experiences: after a force-quit or crash mid-recording with "Mute system audio while recording" on, the Mac stays muted with no clue which app did it or that Inlay is responsible; relaunching Inlay does not fix it. Separately, cancelled-on-quit generations may linger server-side until the 45 s expiry (harmless), and sealed takes finish unannounced (finding 3).
- Confidence: verified-in-code.
- Suggested fix direction: persist muted (device, element) pairs to the client data dir when muting and clear on restore; at launch, if a leftover file exists, un-mute those elements and delete it. Make termination wait (bounded, ~2 s) for the active-take cancel via `.terminateLater`, reusing the existing flush path in `InlayApp.swift:83`.
- Effort: S.

### 7. A helper that cannot load is respawned forever with no backoff or circuit breaker, and proof-helper failures are masked

- Severity: P2
- Evidence:
  - `beginWarmup` is re-invoked from every health response while speech is not loaded (`Server/src/generation-service.ts:359`), from `create` (`Server/src/generation-service.ts:436`), and after every processing job (`Server/src/generation-service.ts:1028`). Its only guards are `stopping`, an in-flight `warming` flag, and in-flight processing (`Server/src/generation-service.ts:1245`); the flag clears in `finally` (`Server/src/generation-service.ts:1266`), so the next trigger starts a fresh attempt. The client polls health every 5 s (`Sources/Inlay/InlayController.swift:253`). There is no attempt counter, delay, or "failed permanently, stop trying" state — `speechLoadError` is recorded (`Server/src/generation-service.ts:1255`) but never consults the decision to retry.
  - If speech loads but the Qwen helper fails, the error handler finds `speechLoaded == true` and sets `speechLoadError = undefined` (`Server/src/generation-service.ts:1258`): the proof failure's reason is discarded, surfacing only as health's generic "Unavailable; deterministic text is preserved." (`Server/src/generation-service.ts:374`). Combined with finding 5, the actual Qwen load error (missing metallib, wrong model layout, GPU init failure) exists nowhere after the fact.
- What the user experiences: a broken model install (the exact failure `README.md:50` warns about during upgrades) leaves the server process spawn-crashing a multi-GB model load attempt indefinitely, burning CPU/GPU/disk on the machine that may also be the user's Mac, while health just says models are unavailable. A fast-crashing helper loops at poll cadence; a hanging one loops at the 120 s load timeout (`Server/src/inference/native-inference.ts:48`).
- Confidence: verified-in-code for the loop and masking; resource impact inferred.
- Suggested fix direction: exponential backoff with jitter between warmup attempts per helper, a latch after N consecutive load failures that requires a config/preferences change (or an explicit retry nudge from health only after the backoff elapses) to try again, and a separate retained `proofLoadError` surfaced in health's proofreading message.
- Effort: S.
- Related good behavior (verified): once loaded, a wrong-file speech model is caught by the pin check with an actionable message (`Server/src/inference/native-inference.ts:231`), and readiness correctly distinguishes missing assets from unloaded ones (`Server/src/inference/native-inference.ts:188`).

### 8. Disk-full arrives unannounced after unbounded growth, and the seal step can still destroy a fully uploaded take

- Severity: P2
- Evidence:
  - Retention is unbounded by design: inference audio is always kept, original audio defaults on, "there is no automatic history expiry" (`docs/architecture.md:70`; inventory confirms no retention code). The only storage guard is a hard 100 MiB free-space floor checked at create and per chunk (`Server/src/storage.ts:95`, call sites `Server/src/generation-service.ts:445`, `Server/src/generation-service.ts:590`). Health reports storage only as a boolean collapsed into "Server storage is unavailable or full." (`Server/src/generation-service.ts:337`); nothing read in the client surfaces archive size or warns before the floor is hit, so the first symptom is dictation refusing to start.
  - Sealing then needs up to a second full copy of each stream: `seal` streams `<kind>.raw` into `<kind>.wav.partial`, syncs, renames, and only then deletes the raw (`Server/src/generation-service.ts:928`, rename/rm `Server/src/generation-service.ts:984`). A stream may legally be up to 256 MiB (`Server/src/generation-service.ts:584`) — far beyond the 100 MiB headroom the gate guarantees, and realistic for a multichannel interface at high sample rate (8 ch × 192 kHz float32 ≈ 6 MB/s per stream). Seal never re-checks free space for the copy.
  - When sealing fails, the catch marks the record failed, then `cleanPartial` deletes the raw files (`Server/src/generation-service.ts:693`) — the one complete copy of the audio — so a transient full-disk during seal permanently destroys a take that was 100% uploaded. If the failure-save itself fails, the failed state exists only in memory via `publish` (`Server/src/generation-service.ts:697`) and the on-disk record still says `receiving` until restart reconciliation.
- What the user experiences: months of always-kept dual audio quietly fill the disk; dictation then stops working with a generic storage message and no in-app way to see or reclaim space short of deleting history items one by one. Near the boundary, individual long/multichannel takes can upload fine and then be destroyed at seal time.
- Confidence: verified-in-code for mechanism; the multichannel size scenario is arithmetic from the admitted format bounds (`Server/src/generation-service.ts:511`), not observed.
- Suggested fix direction: check projected seal space (raw bytes × 1 per stream) in `finish` before sealing; on seal failure keep the raw files and mark the record retryable instead of deleting them; surface archive disk usage and a low-space warning well above the floor (health already computes the disk stat), and consider an owner-set retention/size cap for original audio (decision below).
- Effort: S (seal check + keep-raw) to M (usage surfacing/retention).

### 9. Pressing the hotkey while the server/mic is unavailable steals focus to the Inlay window

- Severity: P2
- Evidence: `beginDictation`'s three refusal paths (server not ready, mic permission, no microphone) all call `onShowWindow?()` in addition to showing the HUD error (`Sources/Inlay/InlayController.swift:852`). `showWindow` activates the app and makes its window key (`Sources/Inlay/InlayApp.swift:126`). Every press repeats this — there is no rate-limiting or "already shown" check in the read code.
- What the user experiences: server is down; the user presses Right Option in their editor to dictate; Inlay's window jumps to the front and takes keyboard focus. Even after they fix the server, their insertion context is gone and must be re-established. A user who reflexively presses the key a few times (the natural response to "nothing happened") gets repeatedly yanked out of their work. This also makes the failure state self-concealing: the app that broke focus is not obviously the app whose server is offline.
- Confidence: verified-in-code.
- Suggested fix direction: show only the HUD error on hotkey-initiated refusals; reserve window presentation for menu/window-initiated actions (e.g. Test Microphone button) or first-ever refusal. The HUD already carries the same message via `showError` (`Sources/Inlay/InlayController.swift:1195`).
- Effort: S.

### 10. When the insertion target is gone, the clipboard fallback is defeated by any clipboard use during the wait — and the explanation vanishes in 4 seconds

- Severity: P2
- Evidence:
  - Delivery re-validates the captured field (`Sources/Inlay/System/TextInserter.swift:198`, validation `Sources/Inlay/System/TextInserter.swift:234`); a changed/gone target degrades to clipboard copy (`Sources/Inlay/System/TextDeliveryTransaction.swift:74`), but only via `copyInstead`/`keepBackup`, which require that every pasteboard change since the **recording-start** change count be Inlay-owned (`Sources/Inlay/System/TextDeliveryTransaction.swift:188`, `Sources/Inlay/System/TextDeliveryTransaction.swift:194`, `Sources/Inlay/System/TextDeliveryTransaction.swift:243`; count captured at `Sources/Inlay/InlayController.swift:863`). If the check fails the outcome is `.failed` ("Your words are ready to copy.").
  - The safety intent is sound (never clobber a clipboard the user has since used), but queueing makes the window long: sealed takes process serially (`Server/src/generation-service.ts:1014`) and delivery additionally waits for any active capture to end (`Sources/Inlay/InlayController.swift:1025`, `Sources/Inlay/InlayController.swift:1161`). Minutes can pass between key-press and delivery, during which any copy action in any app — including the user copying something while waiting — silently disables the fallback.
  - The resulting `.failed` state is shown on the HUD which auto-dismisses after 4 s (`Sources/Inlay/InlayController.swift:1037`), and the transcript's durable home is again only shared history (finding 3); `lastTranscript` persists in the window (`Sources/Inlay/InlayController.swift:1144`, copy action `Sources/Inlay/InlayController.swift:766`) but nothing prompts the user there.
- What the user experiences: dictate into an app, get distracted or copy a link while the server works through the queue, target app quits or focus moves; result arrives, cannot insert, cannot copy (clipboard "changed"), HUD shows a failure for 4 s while the user may be looking elsewhere. The words are safe in history but the user has no signal that recovery is "open Inlay → History/Dictation → copy" versus "it is lost".
- Confidence: verified-in-code for the mechanism; how often users hit it is inferred.
- Suggested fix direction: when insertion and guarded copy both fail, keep a persistent, non-dismissing affordance (menu-bar badge and/or keep HUD until dismissed) saying the text is saved and one click copies it; optionally ask-once semantics: an explicit user click on "Copy result" in that moment is consent to overwrite the clipboard, which the current guard lacks a path for.
- Effort: S–M.

## Verified strengths (so severity above is calibrated)

- Admission is fail-fast and honest: no recording starts unless server is ready **and** API-matched, mic permission is granted, and a device resolves (`Sources/Inlay/InlayController.swift:852`); server re-checks readiness and disk before accepting (`Server/src/generation-service.ts:412`).
- `finish` is idempotent and retried by the client (`Sources/Inlay/ServerClient.swift:236`, `Server/src/generation-service.ts:634`); chunk uploads are sequenced, acknowledged, exactly-replayable, and conflict-rejecting (`Server/src/generation-service.ts:482`).
- Durable writes are temp-file + fsync + rename + directory fsync at 0600/0700 with symlink refusal (`Server/src/storage.ts:51`), and the data-dir lock is a crash-safe `flock` that cannot go stale (`Server/src/data-lock.ts:33`, comment `Server/src/data-lock.ts:49`).
- Proofreading failure degrades to deterministic text instead of failing the take (`Server/src/generation-service.ts:1192`), helpers are timeout-bounded with SIGTERM→SIGKILL retirement (`Server/src/inference/helper-process.ts:323`, `Server/src/inference/helper-process.ts:357`), and event-stream drop recovery exists (finding 3 is about its bound, not its absence).
- Permission UX at rest is real: missing grants open guided help on launch (`Sources/Inlay/InlayApp.swift:67`), the event tap self-recovers from macOS disabling it (`Sources/Inlay/System/HotkeyMonitor.swift:303`) with a 2 s health watchdog (`Sources/Inlay/System/HotkeyMonitor.swift:262`), and unsafe destinations never get blind typing (`Sources/Inlay/System/TextDeliveryTransaction.swift:76`).

## Questions for owner

- Is "interruption = total loss, no offline queue" (`docs/architecture.md:33`) still the intended contract for 3-minute takes, or should chunk retry / partial-finish / local-file re-upload become product behavior? This decides whether finding 1 is a P1 defect or accepted design that only needs louder user messaging.
- Should server restart requeue sealed generations (finding 2), and is a user-facing "transcribe again" action for failed records with sealed audio desirable regardless?
- After an app relaunch, what should a completed-but-undelivered dictation do: silent history (today), badge + copy affordance, or delivery to the _current_ field after explicit confirmation? Auto-paste conflicts with the captured-destination safety model, so this is a product call (finding 3).
- What is the retention expectation for always-kept inference + original audio — keep forever until the disk floor (today), an owner-visible usage meter + manual pruning, or an optional age/size cap (finding 8)?
- Should server logs be allowed to contain operational metadata (device names, generation IDs, error stacks) given the current privacy posture deliberately discards helper stderr and transcripts never leave metadata files? Finding 5's fix needs that boundary stated.
- Is focus-stealing on unavailable hotkey press (finding 9) intentional discoverability, or should refusals be HUD-only?

- The exact user-visible timing bound in finding 3 depends on `URLSession` timeout interaction with NDJSON `bytes` iteration, which I read but did not measure.
- The Swift reference server (`Sources/InlayServerKit`) was not re-audited for these reliability properties; findings cite the shipped TypeScript server. Its helper-diagnostics handling differs slightly (`Sources/InlayServerKit/HelperProcess.swift:230` was seen only as a search hit, not read in full), so no claim is made about it.
- Views were read only where the controller connects to them (`lastTranscript`, history actions); I did not fully read `HistoryPage.swift`/`DictationPage` bodies, so claims about what history UI offers (copy/transcribe-again affordances) rest on the controller methods at `Sources/Inlay/InlayController.swift:664`–`Sources/Inlay/InlayController.swift:690` and the full server route table, not on the view layer.
- `RecordingWriter.process` beyond its format/interval guards (`Sources/Inlay/System/AudioRecorder.swift:500`+) and the underlying `AudioCaptureSession`/`InputOnlyAudioUnit` bodies were not read in full; local-capture-file salvage feasibility in finding 1 is inferred from the writer's creation/finalization code that was read.
- Signal handling under the packaged runners (systemd unit, Docker/tini, `run-dev.sh`) was not inspected for this file; finding 2 covers the in-process shutdown/restart semantics only.
